# Bug Tracker

Move the public **bug tracker** — the separate GitHub repo where users and testers file bug reports, feedback, and feature requests against a shipped product — through its actionable queue one issue at a time: inspect, grill, verdict, next.

This is `/triage` for public reports: `/triage` works this repo's own tracker, `/bug-tracker` works a separate tracker repo full of raw reports, with the source code in the current working directory. The label taxonomy it drives is the one `/init-bug-tracker` creates.

Every comment posted to the tracker during a run starts with:

```
> *This was generated by AI during bug-tracker triage.*
```

## Resolve the tracker repo

In order:

1. An explicit argument: `/bug-tracker <owner/repo>`. A bare issue number (`/bug-tracker 42`) resolves against the tracker below and jumps straight to step 2.
2. A tracker already recorded for this repo — the `### Bug tracker` sub-block under `## Agent skills` in `CLAUDE.md` or `AGENTS.md`.
3. Ask the maintainer which repo holds the reports, then record it there so the next run doesn't ask again.

If the taxonomy is missing or looks stale on the tracker (labels the workflow names don't exist), suggest the maintainer run `/init-bug-tracker` first.

## Filter: actionable vs waiting

An issue is **actionable** when all of these hold:

1. State is `OPEN`.
2. It is not waiting on the reporter — no `needs-info`, or the reporter has commented after `needs-info` was applied.
3. It matches one of: unlabeled (never triaged); `needs-triage`; `ready-for-agent` or `ready-for-human`; or a `bug` / `enhancement` / `feedback` label with no blocking label.

**Ignored:** `needs-info` without reporter activity, `in-progress` with an active assignee, `wontfix`.

## Workflow

### 1. Fetch and present the queue

```bash
REPO="<owner/repo>"
gh issue list -R "$REPO" --state open --json number,title,labels,author,createdAt,updatedAt,comments
```

Sort into queues, oldest first, and present one table (`# | Title | Category | State | Author | Age`):

- **Queue A — needs attention:** unlabeled or `needs-triage`.
- **Queue B — reporter replied:** `needs-info` with reporter comments newer than the last triage note.
- **Queue C — ready for execution:** `ready-for-agent` / `ready-for-human`.

Begin with the oldest issue in Queue A or B; the maintainer may override the pick by naming an issue number.

### 2. Inspect the issue, conversation, and attachments

1. **Read the full conversation and timeline:**
   ```bash
   gh issue view <number> -R "$REPO" --comments
   ```
   Read the initial description, environment details (OS, version), reproduction steps, and every subsequent comment and reply from the reporter, testers, and maintainers. Parse any prior triage notes so you don't re-ask what was already resolved.

2. **Extract and inspect attachments (screenshots, sample files, logs):**
   - Parse all URLs, image markdown (`![...](url)`), GitHub asset uploads (`https://github.com/user-attachments/assets/...` or `https://github.com/.../assets/...`), and attached logs from the issue body and comments.
   - **Screenshots & UI images**: Download and visually inspect via multimodal `Read` (or curl to `/tmp/` and inspect) to examine error messages, visual clipping, incorrect canvas state, or unexpected UI dialogs.
   - **Sample PDFs & documents**: Download sample files to `/tmp/` (e.g., `curl -sL "<url>" -o /tmp/issue-<number>-sample.pdf`) and inspect their structure (PDF header, corrupt streams, annotation objects) using local tools or pdf-lib scripts.
   - **Console logs & crash reports**: Inspect full stack traces, IPC call names, unhandled rejections, and version info.

3. **Cross-reference the source** in this working directory: locate the relevant subsystem, check related files, recent commits, and existing tests. Trace the exact code path indicated by the logs, attachments, or reproduction steps. Note whether the reported behaviour reproduces and whether it's already implemented.

### 3. Grill to a verdict

Run the `/grilling` skill on this one issue — a round of questions at a time, every question carrying your recommendation:

```markdown
### 🔍 Triaging issue #<number>: <Title>

**Reporter**: @<author> | **Labels**: `<label1>`, `<label2>`

❓ **Q1 — Classification & scope**: Is this a genuine bug in `<component>`, or an enhancement / expected behaviour?
➡️ **Recommendation**: Bug in `<component>`, caused by <reason>.

❓ **Q2 — Severity & priority**: Which of `priority:critical` / `priority:high` / `priority:medium` / `priority:low`?
➡️ **Recommendation**: `priority:high` — it breaks the standard export workflow.

❓ **Q3 — Triage verdict**: How should this route?
- `ready-for-agent` — well-defined, ready for an agent to fix in the source repo
- `ready-for-human` — needs manual testing, UX design, or an architectural decision
- `needs-info` — missing reproduction steps, sample file, or logs
- `wontfix` — out of scope or working as intended
➡️ **Recommendation**: `ready-for-agent`, with the fix plan attached.
```

Wait for each answer; open new rounds as the answers branch. The session ends when the verdict is settled, and the issue then carries exactly **one state label** (`ready-for-agent`, `ready-for-human`, `needs-info`, or `wontfix`), **one category label**, and `priority:*` plus `area:*` where they're identifiable.

### 4. Apply the verdict

1. **Post the triage summary** (every comment opens with the disclaimer):

   ```markdown
   > *This was generated by AI during bug-tracker triage.*

   ### Triage summary
   - **Category**: `bug`
   - **Area**: `area:export-import`
   - **Priority**: `priority:high`
   - **State**: `ready-for-agent`
   - **Analysis**: <root cause / investigation summary>
   - **Next steps**: <fix plan, or what is being asked of the reporter>
   ```

   For `needs-info`, the questions for the reporter are specific and actionable — name the missing reproduction step, sample file, or log, never "please provide more info".

2. **Update labels** — add the verdict, category, priority, and area; remove `needs-triage`:

   ```bash
   gh issue edit <number> -R "$REPO" \
     --add-label "ready-for-agent,area:export-import,priority:high" \
     --remove-label "needs-triage"
   ```

3. **Close** `wontfix`, duplicate, or invalid issues with the reason in the comment:

   ```bash
   gh issue close <number> -R "$REPO" --reason "not planned" \
     --comment "> *This was generated by AI during bug-tracker triage.*\n\nClosed as out of scope: <why>."
   ```

### 5. Advance

Announce what changed on `#<number>`, show the remaining queue counts, load the next actionable issue, and begin its grilling session. Continue until the actionable queue is empty or the maintainer stops the session.
